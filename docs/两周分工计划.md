本分工表依据：

- 命题子系统第一周进展汇报
- 现有一级题库、校验脚本、统计脚本和演示系统

最终交付范围：

```text
出题 → 校验 → 统计 → 补题 → 再校验/统计 → 入库
                                      ↓
                    按等级抽题、按历史覆盖程度抽题
                                      ↓
                         学生端显示、管理端查询
```

本期以一级题库作为完整验收样本。系统结构应支持后续增加其他等级，但不在十二天内承诺完成全部等级题库。

## 三、共同算法与数据规则

### 1. 逐字拼音结构

每道题使用 `tokens` 保存汉字和拼音的一一对应关系：

```json
{
  "id": "L1-001",
  "level": 1,
  "text": "我姓王，你姓什么？",
  "tokens": [
    {"c": "我", "py": "wǒ"},
    {"c": "姓", "py": "xìng"},
    {"c": "王", "py": "Wáng"}
  ],
  "grammar": ["G1-04"],
  "rec_count": 0,
  "last_selected_at": null
}
```

校验必须包括：

- 汉字数量与 `tokens` 数量一致。
- `tokens[i].c` 与原文本第 `i` 个汉字一致。
- 每个 token 都有拼音和声调。
- 标点不作为需要朗读的汉字，但要保留原文本。
- 多音字由自动生成后人工复核，不能完全依赖 `pypinyin`。

### 2. 题库校验规则

自动校验：

- 字表越界
- 句长越界
- 阿拉伯数字和拉丁字母
- 拼音逐字对应
- 语法点编号合法
- 语法点规则命中
- 重复编号
- 重复文本

人工抽检：

- 语法点是否真正成立
- 句子是否自然、口语化
- 是否适合留学生朗读
- 多音字读音是否正确
- 是否出现为了覆盖字而生造的句子

### 3. 抽题算法

权重公式（2026-11-18 更新）：

```text
w = max(0, C - rec_count)
```

其中 C 为覆盖次数上限（默认 10，可配置）；rec_count 达到 C 的题不再参与抽取。

不直接在全题库中随机抽取，改为两阶段：

1. 先筛选指定等级中 `rec_count` 最低的一批候选题目，例如最低覆盖的前二十题。
2. 再在候选集中按 `w` 加权随机抽取。

抽题排序还要考虑 `last_selected_at`，避免短时间连续返回同一道题。

覆盖口径暂定为：`rec_count` 统计已经成功上传并保存的有效录音数量。录音是否有效、同一学生重录是否计入，必须与学生端和管理端书面统一。

## 四、三人固定分工

### 成员A：数据与命题流水线负责人

负责题目内容、字表语法配置、逐字拼音、校验、统计、补题和最终题库质量。

本人的交付判断标准：题库内容合格、统计达标、报告可复现。

### 成员B：后端、数据库与抽题接口负责人

负责 SQLite 数据库、真实题库导入、题目状态、题目增删改查、入库控制、两种抽题接口和接口测试。

本人的交付判断标准：题目能可靠保存、查询、发布和抽取。

### 成员C：前端、统筹与系统联调负责人

负责命题人员网页、流水线操作页面、抽题测试页面、学生端和管理端联调、演示材料和进度汇总。

本人的交付判断标准：命题人员可以在网页完成操作，其他子系统可以正常使用题目。

## 七、每日协作规则

每天结束前三个人必须共同完成：

1. 提交当天代码或数据成果。
2. 记录实际完成内容。
3. 记录未完成事项和阻塞原因。
4. 用同一份题库和同一套字段测试。
5. 不允许成员各自修改字段名称或接口返回结构。

每日同步格式：

```text
今日完成：
今日产出文件：
已验证功能：
发现问题：
明日必须完成：
```

## 八、优先级原则

如果某天时间不足，按以下顺序保留工作：

1. 一级题库真实校验和统计。
2. 题库真实入库。
3. 按等级抽题接口。
4. 按覆盖程度抽题接口。
5. 学生端显示文本和逐字拼音。
6. 管理端查询题目。
7. 页面美化和非核心交互。

页面美化可以压缩，题库质量、校验结果、入库状态和接口正确性不能压缩。
