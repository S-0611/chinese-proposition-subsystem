# 后端七至九级合并接口改造报告

- 日期：2026-11-23
- 服务：`backend/main.py`，`http://127.0.0.1:8001`
- 结论：`level=8`、`level=9` 现在作为 `level=7` 的别名处理；查询、抽题、校验、统计、发布均正常，不再返回空题库。

## 一、问题

七至九级按标准合并为 `level 7`，配置中：

```json
{"level": 8, "merged_into": 7}
{"level": 9, "merged_into": 7}
```

但后端此前直接用请求的 `level` 查数据库。前端请求 8/9 时数据库只有 level 7，因此返回 `total: 0`，状态看板显示“0/3、0、待接入”。

## 二、改造内容

1. 启动时读取 `data/levels/levelN.json` 的 `merged_into`，建立别名表；支持多跳合并。
2. 新增 `canonical_level()`：把 8/9 归一到 7。
3. 新增 `level_meta()`：响应保留：
   - `level`：实际读写级别（7）
   - `requested_level`：调用方传入的级别（8/9/7）
   - `merged_into`：发生合并时为 7，否则为 null
4. `fetch_items()`、`level_has_data()` 统一按归一后的级别访问数据库。
5. 已覆盖接口：
   - `GET /api/questions`
   - `GET /api/questions/random`
   - `GET /api/questions/recommend`
   - `POST /api/pipeline/validate`
   - `POST /api/pipeline/stats`
   - `POST /api/pipeline/publish`
6. `/api/levels`：
   - 7 级返回 `question_count: 360`、`status: available`。
   - 8/9 返回 `status: merged`、`merged_into: 7`，不重复计算题量。
   - 新增 `merged_groups`：`[{levels:[7,8,9], level:7, question_count:360}]`。
7. `_save_round()` 文件名增加微秒，避免同一秒内 validate/stats 报告互相覆盖。
8. 前端状态看板同步改为只展示合并后的 `七—九级` 一行；说明文字改为“后端按 level 7 合并存储和校验”。

## 三、验证结果

### 查询

```http
GET /api/questions?level=8&status=published
GET /api/questions?level=9&status=published
```

结果：

1. 均返回 `total: 360`。
2. `level: 7`、`requested_level: 8/9`、`merged_into: 7`。
3. 题目 ID 均为 `L7-*`，题目对象 `level` 均为 7。

### 抽题

```http
GET /api/questions/random?level=8&n=5
GET /api/questions/recommend?level=9&n=5
```

结果：均返回 5 题，全部为 `L7-*`，响应带 `requested_level` 和 `merged_into`。

### 校验与统计

```http
POST /api/pipeline/validate?level=8
POST /api/pipeline/stats?level=9
```

结果：

1. 校验：360 题合格，0 不合格，`verdict: pass`。
2. 统计：新增字覆盖 1121/1200，语法 148/148，`verdict: pass`。
3. 报告保存到 `reports/level7/`，不会写到 level8/9。

### 发布

```http
POST /api/pipeline/publish
{"level": 8}
```

结果：`ok: true`、`level: 7`、`requested_level: 8`、`merged_into: 7`、`published_count: 0`（题库已全部发布，重复发布无副作用）。

## 四、调用建议

1. 新客户端直接使用 `level=7`。
2. 旧客户端传 8/9 仍可用，后端自动归一，不需要改请求。
3. 客户端应以响应中的 `level` 作为实际等级；`requested_level` 仅用于追踪原请求。
4. 不要按 8/9 分别建库或重复导入；七至九级只有一个题库。

## 五、页面旧数据缓存修复（19:42）

用户反馈页面仍显示 `7 级：该等级题库尚未完成`。检查发现截图中的题目数 `303 / 361 / 548 / 691 / 760 / 1174` 是旧题库文件数量，不是当前数据库的 `256 / 361 / 548 / 691 / 384 / 433`，说明浏览器复用了旧的 `/api/levels`、`/api/questions` 响应。

已修复：

1. 后端所有 `/api/` 响应增加 `Cache-Control: no-store, no-cache, must-revalidate, max-age=0`、`Pragma: no-cache`、`Expires: 0`。
2. 前端 `propositionFetch()` 强制 `cache: 'no-store'`。
3. `index.html` 的 `app.js`、`data.js` 增加版本查询参数，避免旧 JS 缓存。
4. 本地浏览器实测：状态表 7 行，七—九级 `360 / 已入库`；选择七—九级后题目表加载 360 题；推荐抽题返回 `L7-020`。
